Глава 45: Базы данных и большие данные

Базы данных — организованное хранилище структурированных данных с механизмами управления целостностью, безопасностью и производительностью. Большие данные (Big Data) — наборы данных, характеризующиеся объёмом (Volume), скоростью (Velocity) и разнообразием (Variety), обрабатываемые распределёнными системами.

1. Реляционные базы данных и SQL

Реляционная модель (Codd, 1970)

Данные организованы в отношения (таблицы) с кортежами (строками) и атрибутами (столбцами). Ключевые свойства:

  • Целостность сущности: каждая строка уникальна (первичный ключ)
  • Целостность ссылок: внешние ключи ссылаются на существующие записи
  • Нормализация: устранение избыточности (1НФ → 2НФ → 3НФ → BCНФ)

ACID-свойства транзакций

$$\text{ACID} = \underbrace{\text{Atomicity}}_{\text{атомарность}} \times \underbrace{\text{Consistency}}_{\text{согласованность}} \times \underbrace{\text{Isolation}}_{\text{изоляция}} \times \underbrace{\text{Durability}}_{\text{долговечность}}$$

Утверждение 1: Теорема CAP

В распределённой системе невозможно одновременно гарантировать все три свойства:

$$\text{Consistency} + \text{Availability} + \text{Partition tolerance} \leq 2$$

Доказательство: При сетевом分区 (Partition) либо один узел недоступен (нарушение Availability), либо данные на узлах расходятся (нарушение Consistency). Трилемма CAP определяет дизайн-пространство распределённых СУБД.

SQL: структурированный язык запросов

-- Агрегация с оконными функциями
SELECT department,
       AVG(salary) OVER (PARTITION BY department) AS avg_salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rank
FROM employees
WHERE hire_date > '2020-01-01'
ORDER BY department, rank;

Индексация и B-деревья

Утверждение 2: Сложность поиска в B-дереве

Поиск в B-дереве порядка $m$ с $n$ ключами:

$$T_{\text{search}} = \BigO(\log_m n) = \BigO\!\left(\frac{\log n}{\log m}\right)$$

При $m = 256$ (типичный порядок): для $n = 10^9$ записей достаточно $\log_{256}(10^9) \approx 3.75$ уровней (4 дисковых обращения).

2. NoSQL-базы данных

Для данных, не вписывающихся в реляционную модель (полуструктурированные, иерархические, графовые), используют NoSQL-системы.

Типы NoSQL

Ключ-значение

Redis, DynamoDB, Riak. Максимальная производительность: $T = \BigO(1)$ для get/set по ключу.

Документная

MongoDB, CouchDB. Хранение JSON/BSON-документов с гибкой схемой.

Колоночная

Cassandra, HBase. Оптимизация для аналитических запросов по столбцам.

Графовая

Neo4j, ArangoDB. Моделирование связей: $G = (V, E)$, traversal за $O(|E|)$.

BASE vs ACID

Утверждение 3: Модель BASE

Для горизонтально масштабируемых систем используется модель BASE:

  • Basically Available — система доступна, но может возвращать устаревшие данные
  • Soft state — состояние может изменяться со временем без внешних вызовов
  • Eventually consistent — при отсутствии записей все узлы сходятся к одной версии

Доказательство (теорема PACELC): При Partition → choose A или C; иначе → choose L (latency) или C (consistency). Формально:

$$\text{PACELC: } \begin{cases} \text{Partition} \Rightarrow \text{choose } (A, P) \text{ или } (C, P) \\ \text{Else} \Rightarrow \text{choose } (L, E) \text{ или } (C, E) \end{cases}$$

Sharding и репликация

Sharding (горизонтальное分区) разбивает данные по ключу $k$:

$$\text{shard}(k) = h(k) \mod N$$

где $h$ — хэш-функция, $N$ — число шардов. Проблема: при добавлении узлов $N \to N+1$ происходит $O(n)$ перемещение данных. Consistent hashing решает эту проблему: при добавлении узла перемещается только $1/N$ данных.

3. MapReduce и Hadoop

Парадигма MapReduce (Dean & Ghemawat, 2004)

Утверждение 4: Параллельная обработка данных

MapReduce разбивает задачу на два этапа:

$$\text{Map}: (k_1, v_1) \to \text{list}(k_2, v_2)$$
$$\text{Reduce}: (k_2, \text{list}(v_2)) \to \text{list}(v_3)$$

Скорость: При $M$ мапперах и $R$ редьюсерах время обработки $N$ записей:

$$T = \BigO\!\left(\frac{N}{M} + N + \frac{N}{R}\right)$$

Пример: Подсчёт слов

// Map phase
function map(doc) {
    for (word of doc.split(/\s+/)) {
        emit(word, 1);
    }
}

// Reduce phase  
function reduce(key, values) {
    return values.reduce((a, b) => a + b, 0);
}
// word → count

Утверждение 5: Закон Амдала для MapReduce

При $p$ — доля параллельной части, $S$ — ускорение:

$$S(p) = \frac{1}{(1-p) + \frac{p}{N}} \leq \frac{1}{1-p}$$

Даже при $N \to \infty$ ускорение ограничено $1/(1-p)$. Для MapReduce $p \approx 0.95$, поэтому $S_{\max} \approx 20$.

4. Apache Spark

Resilient Distributed Datasets (RDD)

Spark заменяет disk-based MapReduce на in-memory вычисления:

$$\text{Spark speedup} = \frac{T_{\text{Hadoop}}}{T_{\text{Spark}}} = \frac{10 \times \text{disk I/O}}{1 \times \text{RAM}} \approx 10\text{–}100\times$$

Утверждение 6: Линейность RDD

RDD (Resilient Distributed Dataset) — неизменяемое распределённое коллекция элементов, обрабатываемое параллельно. Ключевое свойство: lineage — история трансформаций для восстановления при сбоях:

$$\text{RDD} = \text{ partitions} \times \text{ transformations} \times \text{ lineage}$$

При потере分区 Spark воссоздаёт её из lineage, а не из checkpoints.

API Spark

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, avg, count

spark = SparkSession.builder.appName("Analytics").getOrCreate()
df = spark.read.parquet("hdfs:///data/events")

result = (df
    .filter(col("event_type") == "purchase")
    .groupBy("user_id")
    .agg(count("*").alias("purchases"),
         avg("amount").alias("avg_amount"))
    .orderBy(col("purchases").desc()))

result.show(20)

5. Хранилища данных (Data Warehousing)

Архитектура хранилища

ETL (Extract, Transform, Load) pipeline:

$$\text{Sources} \xrightarrow{E} \text{Staging} \xrightarrow{T} \text{Transform} \xrightarrow{L} \text{Data Warehouse}$$

Схемы данных

Звёздная схема

Факты + измерения. Быстрые JOIN для аналитических запросов.

Снежинка

Нормализованные измерения. Меньше избыточности, сложнее запросы.

Data Vault

Hubs + Links + Satellites. Максимальная гибкость для аудита.

Лента (Lakehouse)

Delta Lake / Iceberg. ACID поверх object storage.

Утверждение 7: Формула стоимости хранения

Стоимость $C$ данных в $D$ лет при объёме $V$ ТБ и ежегодном росте $r$:

$$C = V \cdot c_{\text{TB}} \cdot \sum_{i=0}^{D-1} (1+r)^i = V \cdot c_{\text{TB}} \cdot \frac{(1+r)^D - 1}{r}$$

При $V = 100$ ТБ, $c = 23\$/$ТБ/год, $r = 0.3$, $D = 5$: $C \approx 100 \times 23 \times 7.14 \approx 16{,}400\$$. Экономия от компрессии (ratio 3:1): $\sim 5{,}500\$.

6. ML-пайплайны и feature engineering

Инфраструктура ML-пайплайна

Типичный ML-пайплайн включает:

$$\text{Data} \to \text{Feature Eng} \to \text{Training} \to \text{Evaluation} \to \text{Serving} \to \text{Monitoring}$$

Утверждение 8: Feature Store

Feature Store — централизованное хранилище признаков, обеспечивающее:

  • Consistency: одинаковые признаки для обучения и инференса
  • Reusability: переиспользование признаков между моделями
  • Versioning: версионирование признаков и моделей
  • Online/Offline:低延迟 для online, batch для offline

Примеры: Feast, Tecton, Hopsworks.

Утверждение 9: Теорема о данных

Манифест данных (Бремен, 2012): «Модель не лучше данных, на которых она обучена.» Формально: для модели $f$ и данных $D$:

$$\text{Error}(f, D_{\text{test}}) \geq \text{Error}(f^*, D_{\text{test}}) - \text{bias}(D_{\text{train}}, D_{\text{test}})$$

Где $f^*$ — оптимальная модель, $\text{bias}$ — расхождение между train и test распределениями.

7. Временные ряды и потоковая обработка

Apache Kafka

Распределённый стриминговый брокер сообщений:

$$\text{Producer} \to \text{Topic (Partitions)} \to \text{Consumer Group}$$

Пропускная способность: до $10^6$ сообщений/сек. Долговечное хранение (retention policy).

Утверждение 10: SLA потоковой обработки

Для потоковой обработки с задержкой $L$ и пропускной способностью $T$:

$$L \cdot T \leq B$$

Где $B$ — буфер памяти. Типичные значения: Kafka — $L \sim 10$ мс, $T \sim 10^6$/с; Flink — $L \sim 1$ мс, $T \sim 10^5$/с.

8. Резюме главы

Базы данных и большие данные — фундамент современной информатики. Ключевые концепции:

  • Реляционная модель + SQL обеспечивают ACID-гарантии для транзакций
  • NoSQL-системы решают проблемы масштабирования (CAP-теорема)
  • MapReduce/Hadoop — парадигма пакетной обработки данных
  • Spark — in-memory вычисления (10–100× быстрее Hadoop)
  • Data Warehousing — ETL-пайплайны и аналитические запросы
  • ML-пайплайны связывают данные с моделями через Feature Store
  • Потоковая обработка (Kafka, Flink) — реальное время
